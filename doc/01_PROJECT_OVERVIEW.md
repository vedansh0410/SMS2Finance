## 1. Problem Definition & Real-World Motivation

In modern mobile banking and digital payment ecosystems—especially within India's Unified Payments Interface (UPI) infrastructure—Short Message Service (SMS) notifications generated by financial institutions serve as the primary, real-time notification mechanism for consumer transactions. Every debit card swipe, UPI QR scan, ATM cash withdrawal, IMPS transfer, and salary credit produces a notification SMS.

However, extracting structured transaction logs from raw mobile SMS presents three significant engineering and research hurdles:

1. **Extreme Distractor Noise**: A typical user's mobile inbox contains thousands of messages, where legitimate financial debit/credit alerts are heavily outnumbered by:
   - Transient authentication messages (One-Time Passwords / OTPs).
   - Marketing spam, personal loan pre-approvals, and credit card sales pitches.
   - Non-financial telecom alerts and personal communications.
2. **Privacy & Bandwidth Overhead**: Transmitting a user's entire uncurated SMS inbox to a central server incurs substantial network bandwidth overhead and presents serious privacy risks, exposing private messages, authentication credentials, and personal contacts to remote cloud storage.
3. **Template Fragility vs. Contextual Variance**: Financial institutions routinely change phrasing and formatting. Pure deterministic regular expressions break when a bank modifies spacing or template syntax. Conversely, standalone statistical Named Entity Recognition (NER) models struggle with rigid structural strings like 12-digit Retrieval Reference Numbers (RRNs) and floating-point rupee values.

## 2. The FinSight AI Solution

**FinSight AI (SMS2Finance)** solves these challenges through an end-to-end multi-tier pipeline:

```text
[ Android Device (Edge) ]
       │  1. Telephony Inbox Query (30-day window)
       │  2. Algorithm 1: Edge-Device Level-1 Heuristic Bank Filter
       │     (Drops OTPs, spam, and non-bank messages locally)
       │  3. Incremental Timestamp Checkpoint (`lastSync`)
       ▼
[ Spring Boot Java Backend ]
       │  4. Ingestion Endpoint (POST /api/sms)
       │  5. Raw Ingestion Persistence (`sms_messages` in PostgreSQL)
       │  6. REST Dispatch to Python ML Engine (POST /internal/parser/parse)
       ▼
[ Python AI/ML Engine (FastAPI) ]
       │  7. Deterministic Regex Catalog (Amount, RRN, Account, UPI, Balance)
       │  8. Contextual NER Token Classifier (Merchant descriptors, Intent)
       │  9. Algorithm 2: Conflict-Aware Entity Reconciliation
       │ 10. Algorithm 3: Tiered Financial Deduplication (RRN + Jaro-Winkler)
       ▼
[ Spring Boot Relational Datastore ]
       │ 11. Transaction Persistence (`financial_transactions` in PostgreSQL)
       │ 12. Transaction Query & Dynamic Aggregation APIs
       ▼
[ React / TypeScript Dashboard ]
          13. Real-time KPIs, Inflow/Outflow Trends, Bank Distributions
          14. Full-text Search, Filtering, and Extraction Provenance Inspector
```

## 3. Target Financial Entities

The pipeline extracts and reconciles 9 canonical financial entities for every recognized banking notification:

| Entity Name | Definition / Role | Typical Examples | Primary Source |
|---|---|---|---|
| `AMOUNT` | Transactional numeric monetary value | `Rs. 849.00`, `INR 75,000`, `₹1,499.50` | Deterministic Regex + NER Check |
| `MERCHANT` | Beneficiary entity or commercial payee | `Swiggy`, `Amazon India`, `Zomato`, `Reliance Digital` | Contextual NER Model |
| `RRN` | Retrieval Reference Number / UTR / Txn ID | `312984920194`, `429184019283` | Deterministic Regex ($\ge 6$ digits) |
| `ACCOUNT_LAST_FOUR`| Masked source or destination bank account | `4821`, `9021`, `1140`, `1541` | Deterministic Regex (`XX1234`, `**4821`) |
| `TRANSACTION_TYPE` | Direction of funds transfer (`DEBIT`, `CREDIT`) | `DEBIT` (spent/paid), `CREDIT` (refund/salary) | Rules + Contextual NER |
| `BANK_BALANCE` | Post-transaction ledger or available balance | `Rs. 42,150.00`, `INR 12,450.50` | Deterministic Regex |
| `BANK_NAME` | Financial institution originating the SMS | `HDFC Bank`, `State Bank of India`, `ICICI Bank` | Header Substring Match + Rules |
| `UPI_ID` | Virtual Payment Address (VPA) of payee | `swiggy@okhdfcbank`, `user@icici` | Deterministic Regex |
| `PAYMENT_DATE` | Transaction timestamp / epoch value | `2024-10-06T14:32:00Z` | Device Timestamp / Parsed Date |

## 4. Key Empirical Achievements

Evaluated against a curated, differentially anonymized benchmark of **2,500 messages** across 6 major Indian banking institutions:

* **Edge Bandwidth Reduction Ratio ($\Delta_{BW}$)**: **32.91%** of raw inbox byte volume is dropped on the edge device without ever leaving the user's phone.
* **Edge False Negative Rate ($FNR$)**: **0.0%**—zero legitimate financial transactions are dropped at the edge level.
* **Extraction Macro F1 Score**: **0.9400** exact span match Macro F1 across all evaluated entity classes using the proposed hybrid reconciliation pipeline (outperforming Regex-only at 0.7490 and standalone NER at 0.7024).
* **Transaction Deduplication Fidelity**: **0.0% False-Merge Rate**, ensuring distinct financial transactions are never mistakenly coalesced.

## 5. Architectural Boundaries & System Policies

1. **Edge Filtering Policy**:
   - Telephony SMS is read locally on the Android device using `Telephony.Sms.CONTENT_URI`.
   - Algorithm 1 filters out non-bank and distractor messages prior to network transmission.
   - Incremental sync relies on `lastSync` stored securely in Android `SharedPreferences`.

2. **Data Layer Policy**:
   - The React frontend **never connects directly to PostgreSQL**. All data access traverses the Spring Boot REST API (`http://localhost:8080/api`).
   - The Spring Boot backend maintains two distinct PostgreSQL tables: `sms_messages` (raw audit trail) and `financial_transactions` (structured ledger).

3. **ML Service Policy**:
   - The AI/ML engine operates as an independent Python FastAPI microservice (`http://localhost:8000`).
   - This maintains clean separation between high-concurrency Java enterprise services and Python's scientific computing stack.

4. **Integration Boundary**:
   - Ingestion is triggered by incoming bank SMS. Direct integrations with private Google Pay / Paytm databases are neither claimed nor required.
